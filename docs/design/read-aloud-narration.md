# Design: content-addressed read-aloud narration (skill-generated, liveview-consumed)

Status: **proposed** (design — implementation in progress; liveview-side LLM call
removed first). Follows the read-aloud speech registry (`server::speakable`).

Goal in one line: the watch-and-listen reader narrates non-prose resources
(diagrams / tables / formulas / code) with text **pre-generated by a skill** and
stored **out of band, content-addressed** — so liveview never calls a model,
tokens are spent only on resources that genuinely need it (never on prose, never
twice on a repeat, never again on something unchanged), and the narration↔source
link survives edits because it's keyed by *content*, not position.

---

## 1. Why this, and what changed

The first cut (`server::speakable`) routed each non-prose unit to an LLM CLI
(`narrate.rs`, `LV_NARRATE_CMD`) **at synth time, inside liveview**. Two problems:

- **It never worked in production.** The deployed `liveview.service` /
  `liveview-sync.service` are hardened (`ProtectHome`, no `claude` on PATH,
  `LV_NARRATE_CMD` unset). The shell-out always failed → silent fallback. The
  only narration that actually ships is the **skill** (`narrate-book` → authored
  `.spoken.md`, the audiobook rendition). liveview itself has never narrated.
- **Even if it ran, it's wasteful.** Synth-time, per-chapter, no dedup, no
  incremental — the same diagram in 50 chapters would cost 50 calls.

So: **move generation to the skill layer** (where the LLM already lives), **store
the result content-addressed**, and make liveview a pure consumer. Remove the
liveview-side LLM logic entirely.

## 2. Two tiers — only spend tokens where a model is actually needed

| Tier | Covers | Generated by | Token cost |
|---|---|---|---|
| **Deterministic (runtime)** | prose verbatim; inline normalization (URL / email / 0x-address / hash / phone → spoken stand-in); image `alt` spoken as-is | liveview, at render (pure Rust) | **zero** |
| **Narrated (pre-generated)** | mermaid / inline-`<svg>` diagrams, GFM + HTML tables, display math, code blocks | a **skill** (Claude), offline | only these |

Prose is **never** sent to a model. The current audiobook `.spoken.md` rewrites
the *whole chapter* — 80–90% of which is prose read aloud verbatim anyway — so
most of its tokens are spent re-emitting prose. This design spends tokens only on
the handful of blocks that can't just be read.

## 3. The heart: a content-addressed key, not a position pointer

A narration is linked to its resource by a hash of the resource's *content*:

```
key = blake3( lang · 0x00 · kind · 0x00 · normalize(resource_src) ) → 16-byte hex
```

- `resource_src` is what `spoken_units` already extracts per non-prose unit: the
  mermaid/code literal, the linearized table, the math literal, the raw SVG.
- `normalize` = trim + collapse all whitespace runs (incl. newlines) to one
  space, so trivial reformatting doesn't invalidate.
- `lang` is in the key because narration is language-specific (a zh book and an
  en book sharing a diagram want zh vs en narration).

Why this is the right link — it satisfies "reliable, not fragile":

1. **Editing prose around a resource, inserting a block, or reordering blocks
   does not change the key** → the narration still resolves. Position pointers
   (line/byte/block-ordinal) would all break here.
2. **The key changes only when the resource itself changes** — exactly when the
   narration *should* be regenerated. It breaks precisely when it should.
3. **Identical resources share one key → one narration.** The corpus repeats
   diagrams/tables/formulas heavily; this dedups them for free (token saving).
4. **Out of band → no structural perturbation.** Unlike an inline `<!--speak-->`
   annotation (which becomes a parsed block and shifts the block ordinals the
   highlight anchors on), the sidecar touches neither the markdown nor the render.

**liveview owns the key function on both ends** — `narrate-plan` emits keys, the
synth resolves keys — so the two never disagree. The skill never computes a key;
it only fills text against keys liveview handed it. One implementation = a link
that cannot drift.

## 4. Storage

### Authoring surface — a per-book, per-lang sidecar (git-tracked, reviewable)

```
books/<slug>/.narration/<lang>.json
{
  "schema": 1,
  "prompt_version": 1,
  "entries": {
    "a3f9c1…": {
      "kind": "diagram",
      "text": "私钥经 secp256k1 得到公钥,公钥取 keccak256 的后 20 字节就是地址。",
      "src_preview": "graph TD; PK --> PUB --> ADDR",
      "model": "claude-…",
      "at": "2026-06-20"
    }
  }
}
```

- Flat content-addressed map → append-only, near-conflict-free, parallel-book safe.
- `prompt_version`: bump to intentionally invalidate all narration after a prompt
  improvement (controlled regen); unchanged → 100% cache hit, zero tokens.
- Committed → narration is **human-reviewable and hand-fixable**, versioned.

### Serving surface — a `narration` table in pg (the server has no corpus)

The thin server reads only pg + rustfs; it cannot read the sidecar file. So
`liveview sync` (which *does* read the corpus) ingests each book's sidecar into a
global, content-addressed table:

```sql
CREATE TABLE narration (key TEXT PRIMARY KEY, kind TEXT, lang TEXT, text TEXT);
```

Global table ⇒ cross-book dedup at the storage layer too. The synth resolves a
unit's narration by `key`.

## 5. The contract (skill ↔ liveview)

```
1. liveview narrate-plan <book> --lang zh         [liveview computes keys]
     → emits the TODO: [{key, kind, src, heading?}] for every non-prose resource
       NOT already in .narration/<lang>.json  (deduped by key, diffed vs sidecar)

2. skill (Claude) reads each src, writes narration per type recipe
     → merges {key → {kind, text, …}} into books/<slug>/.narration/<lang>.json

3. liveview sync  reads chapter.md + .narration/<lang>.json
     → upserts entries into the pg `narration` table (content-addressed, global)
     → bakes text-audio with edge-tts only (no model), narration resolved by key
     → a unit whose key is absent = a silent step-over (narrate-audit flags it)
```

Token efficiency falls out of the contract:
- **prose**: never in the plan → zero tokens.
- **dedup**: the plan is keyed + deduped → a repeated resource appears once.
- **incremental**: the plan diffs against the existing sidecar → only new/changed
  keys are emitted → re-runs cost ∝ change, not book size.
- **batching**: the skill can pack many small resources into one structured call.

## 6. Runtime consumption (sync + synth)

`server::speakable::plan` keeps its per-kind routing but the non-prose arms change
from "build an LLM prompt" to "resolve a key against the narration store":

```
Prose  → normalize_inline()              (deterministic, as today)
Image  → alt verbatim, else silent       (deterministic, as today)
Code   → mermaid? key(diagram) : key(code)
Table  → key(table)        Math → key(math)        Html → svg/table key, else silent
   ⇒ store.get(key) ? Ready(text) : Silent
```

`unit_speech(unit, lang, &store) -> String`. The synth sites (`audio_worker`,
`ensure_text_audio`) load the book's narration (from pg) once per chapter and pass
it in. **`narrate.rs` and every `LV_NARRATE_CMD` path are deleted.**

Sync / highlight stay aligned exactly as today: `idx` orders the audio marks,
`blk` anchors the in-place outline, display `text` is untouched — all derived from
the same `spoken_units` parse. The key only decides *what fills* a non-prose
unit's spoken slot.

## 7. Evaluator

`narrate-audit` already dry-runs `plan`. It gains the store: a non-prose resource
becomes `narrated (stored)` when its key is present, or a warning
`needs-narration (run narrate-plan + the skill)` when absent — so the audit tells
you the exact remaining token spend before you spend it.

## 8. Rollout

1. **liveview LLM removal + key/store/lookup + `narrate-plan`** (this branch).
2. **pg `narration` table + sync ingestion** (a focused migration).
3. **the skill** (`narrate-resources`, or extend `narrate-book`): plan → generate
   → write sidecar.
4. **pilot one book** (ranked by `narrate-audit` richness): generate its sidecar,
   sync, listen, tune the recipes, re-generate (cheap — only the book's unique
   resources).
5. **migrate the corpus**: `narrate-plan` per book → skill fills sidecars →
   `sync --render-version <bump>` invalidates stale audio → worker re-bakes with
   narration. Cost is bounded by the deduped, incremental plan.

## 9. Open choices

- **Dedup scope**: per-book sidecar (simple, review-local) is the authoring
  surface; the pg table is already global, giving cross-book serve-time dedup. A
  shared read-through *authoring* cache (so the skill skips a resource already
  narrated in another book) is a later token optimization.
- **Context in the key**: v1 keys on the resource source alone (max dedup). If a
  bare code snippet needs its surrounding meaning, add the nearest heading as a
  short salt — trades some dedup for quality. Start without; revisit per feedback.
- **prompt_version granularity**: one global version (simple, regen-all) vs
  per-kind versions (regen only the kind whose recipe changed). Start global.
